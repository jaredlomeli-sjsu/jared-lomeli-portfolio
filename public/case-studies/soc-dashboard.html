Case Study

SOC Dashboard — Network Intrusion Monitor

A locally-running Security Operations Center dashboard built on the real CIC-IDS2017 network intrusion dataset — 2.83 million labeled flows in Postgres, 17 Grafana panels provisioned as code, and a Python ETL pipeline that had to fix five real data-quality defects before any of it was trustworthy.

Grafana PostgreSQL Docker Python Data Engineering SOC

The Problem

Most SOC-dashboard side projects I looked at while building this used synthetic or mocked data — which makes the dashboard easy to demo but proves nothing about handling a real, messy dataset. I wanted the opposite problem: take a real, published network-intrusion dataset and get it into a state where a security analyst could actually trust the numbers on screen. That meant the interesting engineering work wasn't the dashboard — it was the data underneath it.

CIC-IDS2017 is a labeled network-flow dataset from the Canadian Institute for Cybersecurity: 2,830,743 flows captured over five days in 2017, covering benign traffic and 14 real attack types (DoS, DDoS, brute force, infiltration, web attacks, port scans, and more). It's widely used in intrusion-detection research, which also means its rough edges are well known if you go looking — I found several the hard way instead.

Architecture

Everything runs locally via Docker Compose — no cloud hosting, no mock data:

Service Image Purpose
postgres postgres:16 Holds the flows table — all 2.8M rows
grafana grafana/grafana-oss:11.4.0 Dashboard UI, auto-provisioned datasource and dashboard

The Grafana datasource and the dashboard itself are both provisioned as code (YAML + a versioned JSON dashboard definition), not hand-built through the UI — so the whole dashboard is reproducible from a clean checkout instead of living only in one browser's session state.

The Data Pipeline

The source data is 8 CSV files straight from CICFlowMeter, the tool that generated the original dataset. Loading them naively into Postgres would have quietly poisoned the dashboard. Three of the defects I found and fixed:

1. Mangled attack labels — a corrupted en-dash character had turned three Web Attack categories into effectively three different strings each, which would have split what should be one attack type across multiple rows in every chart. 

# load_data.py
def normalize_label(label):
    if not isinstance(label, str):
        return label
    label = label.strip()
    if label == "BENIGN":
        return label
    if label.startswith("Web Attack"):
        if "Brute Force" in label:
            return "Web Attack - Brute Force"
        if "XSS" in label:
            return "Web Attack - XSS"
        if "Sql Injection" in label or "SQL Injection" in label:
            return "Web Attack - SQL Injection"
    return label

2. Infinity and negative values in the rate columns — a known CICFlowMeter quirk (division-by-zero on very short flows), not a bug in this pipeline, but Postgres has no use for them. 

# load_data.py
for col in ("Flow Bytes/s", "Flow Packets/s"):
    df[col] = pd.to_numeric(df[col], errors="coerce")
    df[col] = df[col].replace([np.inf, -np.inf], np.nan)
    df.loc[df[col] < 0, col] = np.nan

3. Flow duration in microseconds — technically correct, practically unreadable. A generated column keeps both units without duplicating data or drifting out of sync. 

-- sql/schema.sql
flow_duration_seconds  DOUBLE PRECISION
    GENERATED ALWAYS AS ("Flow Duration" / 1000000.0) STORED

The other two defects: a duplicate Fwd Header Length column in the raw CSVs (verified byte-for-byte identical to the first occurrence before dropping it), and inconsistent leading whitespace in the CSV headers themselves (" Destination Port" vs. "Destination Port") that would have silently broken any exact-match column lookup.

The load itself streams each CSV in 50,000-row chunks through Postgres's COPY FROM STDIN rather than row-by-row inserts, and the whole script is idempotent — it truncates the table before every run, so re-running it after a schema tweak never duplicates rows. End of load, it prints the row counts against the dataset's published totals as a sanity check: 2,830,743 total, 2,273,097 benign, 557,646 attack — all three matched on the real run.

The Dashboard

17 panels total: 3 KPI cards up top, attack-type and attack-family breakdowns, a daily attack timeline, per-port analysis, a behavioral scatter plot, and a raw flow-record table for drilling into individual flows. Four template variables — $day_session, $attack_type, $dest_port, $class — drive every panel, and clicking almost anything (a bar, a pie slice, a KPI card, a table row) sets the matching filter via Grafana data links.

Design decision

The $class filter (All / Benign / Attack) doesn't apply to every panel, and that's deliberate rather than an oversight. Panels where "benign vs. attack" is a meaningful, non-contradictory choice — the KPI cards, the all-traffic port breakdown, the behavioral map, the raw flow table — respect it normally. But panels that are inherently attack-only (Top Attack Type, Attack Family Rollup, Per-Attack-Type Deep Dive) or that already compare benign vs. attack side-by-side within one query (the daily timeline, average packet size, SYN flag rate) intentionally ignore it. Gating those by $class = Benign wouldn't filter them usefully — it would just force a guaranteed-empty chart, since their own query logic already bakes in "attack" or "both classes." Every panel respects the filter that's actually meaningful for its own shape, rather than every panel technically obeying one global toggle.

Known Limitation

The Behavioral Signature Map — a scatter plot of average packet size against flow duration, sized by flow count — uses Grafana's native XY Chart panel with manual field mapping. That panel type only supports coloring points by a numeric field, so I can't color points by attack type (a text field) the way the rest of the dashboard's palette would suggest. The workaround is hovering a point to read its attack type from the tooltip instead of reading it off the color. Not a dealbreaker, but a real constraint of the tool, not a design choice I'd have made if the panel type supported it.

What I'd Do Differently

This is a local-only project by design — I wanted to prove out the data engineering and dashboard design without also taking on cloud hosting costs and security hardening for a portfolio piece. That said, the honest next step before this ever runs anywhere besides my own machine: the Grafana and Postgres credentials are still the Docker Compose defaults, which is fine for a stack that only listens on localhost and is exactly what I'd fix first before any hosted deploy. I'd also add a lightweight test suite around load_data.py's cleaning functions instead of relying on the end-of-run row-count check — that check catches a bad total, not a subtly wrong label mapping.

This project isn't open-sourced yet, so this write-up is based directly on the real, running code rather than a public repo. Have questions about it? Email me — happy to walk through any part of it.
