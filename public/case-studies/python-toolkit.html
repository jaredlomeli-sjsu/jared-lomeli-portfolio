Case Study

Cybersecurity Python Toolkit

Three small Python tools, standard library only — no third-party dependencies — built to practice the "detect and verify" side of security operations by hand: file integrity monitoring, password strength scoring, and SSH brute-force log parsing.

Python Security Log Analysis Cryptography

The Problem

It's easy to read about file integrity monitoring, password policy, and brute-force detection in a study guide without ever touching the mechanics underneath. I wanted the opposite of that — three small, self-contained scripts, stdlib only (hashlib, json, os, re, collections), each one forcing me to actually implement the logic a real security tool would need instead of just describing it.

File Integrity Checker

Recursively SHA-256-fingerprints every file in a target folder, saves the fingerprints as a JSON baseline, then re-hashes on demand and reports each file OK, CHANGED, or MISSING against that baseline — classic FIM logic, the same idea behind the Wazuh FIM module in my Kali/Wazuh lab series, just written from scratch.

Hashing reads the file in 8,192-byte chunks rather than loading it whole, so it doesn't choke on large files: 

# file_integrity_checker.py
def sha256(path):
    h = hashlib.sha256()
    with open(path, "rb") as f:
        for chunk in iter(lambda: f.read(8192), b""):
            h.update(chunk)
    return h.hexdigest()

Verify walks the saved baseline and re-hashes each path — status falls out of a simple three-way comparison: 

# file_integrity_checker.py
for p, original in saved.items():
    current = sha256(p) if os.path.exists(p) else None
    status = "OK" if current == original else "CHANGED" if current else "MISSING"

The screenshot above is a real tamper test: I baselined a sample folder, then modified config.txt, deleted keys.pem, and dropped in an untracked backdoor.sh before re-running verify.

Known limitation

Writing this case study is what made me actually trace through the verify() logic end to end — and it only loops over paths already in the baseline. It never re-walks the folder to check for files that weren't there before. That means the untracked backdoor.sh I added during the tamper test was invisible to this script; it only ever catches modified or deleted files, not new ones. A real FIM tool needs a folder diff against the baseline, not just a baseline replay — I'd add that next.

SSH Brute-Force Log Parser

Scans an auth log for Failed password lines, pulls the source IP out with a regex, tallies attempts per IP with collections.Counter, and flags anything over a configurable threshold as a likely brute-force source: 

# ssh_brute_force_log_parser.py
def find_brute_force(logfile, threshold=10):
    counts = Counter()
    for line in logfile:
        if "Failed password" in line:
            m = re.search(r"from (\d+\.\d+\.\d+\.\d+)", line)
            if m:
                counts[m.group(1)] += 1

    for ip, n in counts.most_common():
        if n >= threshold:
            print(f"  {ip:16s}: {n} failed attempts")

Against the sample 41-line auth log in the repo, this flags 2 of 4 source IPs at a threshold of 10 — 192.168.1.10 at 23 attempts and 10.0.0.5 at 13. The match string is exactly "Failed password", case-sensitive — a small detail, but it's exactly the kind of thing that silently breaks a real log parser if the log format ever changes case.

Password Strength Checker

Scores an input 0–5 against five checks and maps the score to a plain-English verdict: 

# password_strength_checker.py
checks = {
    "length >= 12":  len(pw) >= 12,
    "has lowercase": any(c.islower() for c in pw),
    "has uppercase": any(c.isupper() for c in pw),
    "has digit":     any(c.isdigit() for c in pw),
    "has symbol":    any(not c.isalnum() for c in pw),
}
score = sum(checks.values())
verdict = ["Very Weak", "Weak", "Okay", "Good", "Strong", "Excellent"][score]

Deliberately simple — length and character-class checks, no dictionary or breach-list lookup — since the point was practicing the scoring logic itself, not shipping a production-grade password policy engine.

What I'd Do Differently

Beyond the FIM folder-diff gap above: none of the three scripts have real unit tests, and both the FIM target folder and the password checker's sample input are hardcoded at the bottom of the file rather than taken as CLI arguments — fine for a practice project, the first thing I'd change if these became real tools I used regularly.

This project isn't open-sourced yet, so this write-up is based directly on the real code rather than a public repo. Have questions about it? Email me — happy to walk through any part of it.
